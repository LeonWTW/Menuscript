Initial Understanding
What the project does: Menuscript is a client-only iOS application that translates foreign restaurant menus, explains dishes, and calculates split bills using device orchestration and third-party APIs (Google Gemini, Frankfurter).
Who or what it is intended to support: It supports international travelers who need to understand unfamiliar menus and split bills in their home currency.
Primary workflow or capability: Users capture a menu photo, which is extracted and translated via an LLM, allowing them to browse items, read allergen warnings, build a cart, and calculate a versioned, immutable bill snapshot.

Engineering Strengths
Strength 1: Immutable State Modeling. The implementation of BillSnapshot in Sprint 3 is an outstanding architectural decision. By freezing the exact FX rates, currencies, and line items into opaque, versioned bytes at the time of checkout, the app ensures that historical bills cannot be retroactively corrupted by future settings changes or rate refreshes. This drastically improves data reliability.
Strength 2: Rigorous Privacy and Provider Boundaries. The RuntimeServiceResolver creates an airtight boundary between the MockVisionProvider and the live GeminiProvider. Combined with the GeminiDisclosureGate and Keychain-backed SecretStore, this ensures the app is highly secure and never accidentally leaks user data or API keys during demo modes.
Recommendations or Engineering Questions
Recommendation 1: Implement a Data Retention/Pruning Strategy. The architecture.md file notes that full-resolution (downsampled to 2560px) images are stored indefinitely in SwiftData, which will cause unbounded storage growth for heavy users. This matters because it will eventually degrade device performance and frustrate users. I recommend implementing a retention policy that prunes raw photo data older than a certain threshold (e.g., 30 days) while keeping the lightweight BillSnapshot intact for history.
Recommendation 2: Migrate Automation Scripts to Native XCUITest. The manual verification process currently relies on external host tools like osascript and cliclick to drive UI taps, which resulted in fragile tests due to macOS Accessibility permissions. This matters because it makes continuous integration impossible. I recommend porting these flows into a formal Xcode UI testing target.
Highest-Priority Recommendation
Highest Priority: Implement the photo data retention/pruning strategy.
Why: While XCUITests improve developer experience, unbounded storage growth is a critical user-facing defect. Implementing a pruning mechanism will prevent the app from consuming gigabytes of user storage over time, providing the greatest immediate benefit to the application's professional readiness and longevity.
